## Fidelity Tiers

Keep these tiers separate in reviews:

- KERNAL-trap simulation: intercepts host KERNAL serial routines and directly returns file/directory bytes. This can be correct for normal `LOAD` workflows without modeling IEC waveforms or the drive CPU.
- DOS/file-system simulation: models channel 15, DOS commands, directory/BAM mutation, error codes, and image writes.
- Hardware drive emulation: models the 1541 as its own 6502 computer with ROM/RAM, 6522 VIAs, IEC line timing, GCR bitstream, spindle/head mechanics, and drive-code upload/execution.

The current EMULATORS `Disk1540SeriesSimulation` is a trap-based D64 simulation. It supports D64 connection, device numbers, logical/secondary channel state, directory `$`, file reads, channel 15 status, and some status behavior. Commands `N`, `C`, `R`, `S`, `I`, and `V` are present as command-channel cases but currently report unimplemented.

## Hardware Facts

The 1541 is an intelligent peripheral:

- 6502 CPU, 1 MHz system clock.
- 2 KB RAM, commonly mapped at `$0000-$07FF`.
- 16 KB ROM, mapped as `$C000-$DFFF` and `$E000-$FFFF` ROM halves.
- Two MOS 6522 VIA chips.
- Commodore serial IEC interface with daisy-chain connectors.
- Standard factory device number is 8; hardware alterations can select 9, 10, or 11.
- Standard formatted capacity is about 170 KB on 35 tracks.
- Supported file types include PRG, SEQ, REL, USR, random/direct-access use cases, and directory/status channels.

The service manual describes:

- A 16 MHz crystal divided to derive the 1 MHz CPU clock and variable recording clocks.
- Recording clock zones: tracks 1-17 divide by 13, 18-24 by 14, 25-30 by 15, and 31-35 by 16.
- The spindle motor runs at 300 rpm under speed control.
- The stepper mechanism moves in half-track increments.
- A power-up diagnostic reports flash codes for zero page, DOS ROM, and RAM failures.
- One VIA handles the serial interface; another VIA participates in microprocessor read/write and motor control. Verify exact chip labels/addressing against the selected board revision and ROM.

## IEC And KERNAL Trap Semantics

Audit these together because EMULATORS currently works at this boundary:

- LISTEN/TALK target the selected device number; unrelated devices must ignore the command so another serial peripheral can respond.
- UNLISTEN/UNTALK return to idle without destroying channel state unless DOS semantics require it.
- Secondary addresses select channels 0-15. Channels 0/1 are conventional load/save channels; 15 is the command/status channel.
- OPEN allocates or resets the selected secondary channel. CLOSE releases channels; channel 15 should remain available as the command/status channel.
- The status byte returned to KERNAL must preserve EOF and serial-error bits expected by callers.
- Not-present behavior must set the machine-specific KERNAL status byte used by the trap definition.
- Device numbers for C64/VIC-20/C264 adapters should match the machine's documented allowed range and the local help text.

## CBM DOS Status And Commands

Channel 15 returns comma-separated PETSCII status text ending in carriage return, such as:

- `73,CBM DOS V2.6 1541,00,00` after initialization/reset.
- `00, OK,00,00` after successful operations or after a prior status has been consumed.
- Common errors include syntax errors, file not found, file exists, file not open, no channel, disk full, drive not ready, write protect, illegal track/sector, and read/write errors with track/sector context.

Audit details:

- Reading an empty command should preserve the previous status rather than silently clearing it.
- Reading the status channel usually returns the current status once, then the next read should report OK unless a new error occurs.
- DOS commands are not just strings: `N`, `S`, `C`, `R`, `I`, `V`, `B-*`, `M-*`, `U*`, and `&` have channel, drive, filename, T/S, memory, and execution side effects. Report unimplemented commands as capability gaps unless the requested tier requires them.
- Device-number changes through software are temporary and should not be confused with hardware strap selection.

## D64 Layout

Standard 1541 D64 geometry:

- Tracks 1-17: 21 sectors each.
- Tracks 18-24: 19 sectors each.
- Tracks 25-30: 18 sectors each.
- Tracks 31-35: 17 sectors each.
- 40- and 42-track images are common emulator extensions; tracks 36-42 use 17 sectors each.
- Each sector is 256 bytes. In normal file data sectors, bytes 0 and 1 point to the next track/sector; when byte 0 is 0, byte 1 is the index of the last used byte in the final sector.

Track 18:

- Sector 0 contains the BAM and disk header.
- Bytes 0-1 point to the first directory sector, usually 18/1.
- Byte 2 is the DOS version marker.
- BAM entries are 4 bytes per track: free-sector count plus a 24-bit sector bitmap.
- Disk name is 16 PETSCII bytes padded with `$A0`.
- Disk ID and DOS type follow the disk name.
- Directory sectors contain eight 32-byte entries each.

Directory sector and entry fields:

- Sector bytes 0-1: next directory T/S.
- Entry `n` starts at sector offset `2 + 32*n`.
- Entry offset 0: file type plus flags. Low nibble is DEL/SEQ/PRG/USR/REL; bit 7 distinguishes closed from splatted/unclosed files, bit 6 marks locked files.
- Entry offsets 1-2: first data T/S.
- Entry offsets 3-18: PETSCII filename padded with `$A0`.
- Entry offsets 28-29: file size in blocks, little-endian.

Directory listing returned through `LOAD"$"` is a BASIC program-like byte stream:

- Two-byte load address first.
- Each line starts with a pointer to the next BASIC line and a two-byte line number that displays the block count.
- Disk header, file entries, and `BLOCKS FREE.` lines must match PETSCII formatting enough for BASIC `LIST` output.

## GCR And Physical Media

Only require this for hardware-level or nibble-image features:

- The 1541 uses GCR recording. Four data bits are encoded as five disk bits before writing.
- Valid 4-to-5 GCR codes avoid long runs without transitions; invalid codes should be detectable as byte-decoding/read errors if the implementation models raw disk data.
- Sync is represented by long runs of 1 bits in the serial stream and must be recognized before headers/data blocks.
- Sector headers, data blocks, checksums, gaps, speed zones, and rotation timing matter for copy protection, fast loaders, and uploaded drive code.
- D64 images do not preserve raw GCR timing, weak bits, many read errors, or custom copy-protection layouts. G64/NIB-like formats are needed for that tier.

## Current EMULATORS Checklist

- Does `D64FileTypeIO::canRead` accept exactly the intended image sizes: 35, 40, and 42 tracks?
- Does track/sector offset calculation match the 1541 geometry above?
- Does directory parsing follow the linked directory-sector chain instead of assuming all sectors are valid?
- Does file loading stop on final-sector byte 0 and honor byte 1 as the last used byte?
- Does it guard against invalid/cyclic T/S chains?
- Does `LOAD"$"` include the right load address, header line, file entries, lock/unclosed marks, file types, and blocks-free line?
- Does wildcard matching match CBM DOS behavior for `*` and `?`, including PETSCII names and `$A0` padding?
- Does channel state survive `TALK`/`UNTALK` and repeated reads as a real device would?
- Does channel 15 preserve and clear status at the right moments?
- Are unimplemented command-channel commands surfaced as DOS errors that match expected CBM DOS behavior?
- Are `DRIVE NOT READY`, `FILE NOT FOUND`, `FILE NOT OPEN`, `NO CHANNEL`, EOF, and serial-error statuses observable through the same paths the KERNAL expects?
- If write support is added, are BAM, directory entries, file chains, disk full, write protect, and image persistence updated together?
- If hardware emulation is added, is it a separate drive CPU/ROM/RAM/VIA system rather than folding behavior into host KERNAL traps?
